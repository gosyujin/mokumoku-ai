# 下書きを公開に移すきっかけ(段階5の lint)

## 背景

仕様書の lint は「合格した drafts/ のファイルだけ entries/ へ移動」で、検査は形式(出典の生存、引用の長さ、署名、用語リンク、1日の記事数)だけだった。
「書き終わった」という合図が無いので、そのまま作ると、1本目の記事を読んだ直後の下書きが、次の検査でそのまま公開される。
段階4を動かした初日(2026-11-24)の下書きは、20:57 から 23:07 まで起床のたびに書き足されていて、途中の形はどれも形式上は合格するものだった。

仕様書の検査のうち「AI が書いた旨の署名がある」は、本文の断り書きを削る方針(2026-11-24)と合わない。署名はサイトが記事の冒頭とフッターに入れている。

## 判断

- 公開の合図は、エージェントが front matter に付ける `status: ready` にする(2026-11-24 にユーザーが選んだ)。lint は、この印がある下書きだけを検査する。いつ公開するかも、エージェントが決める。
- 検査の内容:
  - `title`、`date`(ファイル名と同じ日付。未来の日付は不可)、`sources`(1つ以上の公開の Web の URL)がある。
  - 「## 読んだ記事」「## 感じたこと」の節があり、空でない。
  - `sources` と本文の URL が生きている。404 や存在しないサイトは不合格。5xx や時間切れは「次の起床でもう一度」。403 や 429(機械からの取得を断られた)は、警告だけ出して通す。
  - 引用(行頭が `>`)は200文字以内で、引用の中か直後の行に URL がある。
  - 用語リンクを本文に書くなら `https://scrapbox.io/mokumoku-ai/{用語}` の形。`terms` は語だけ。
  - 署名は検査しない(サイト側で満たす)。
- 「1日の記事数が上限以内」は、ファイル名が日付であること(1日1件)と、1回の実行で公開するのは1件まで、という形で満たす。
- 同じ日付の日記が `entries/` にあれば、上書きしない(SOUL.md の境界7)。
- 公開済みの日記への訂正・続きは「追記」として足す(同日に追加で決めた)。
  - 直したい日記と同じ日付の下書きに `kind: addendum` と `status: ready` を付け、本文には足す内容だけを書く。
  - lint は、日記の末尾に `## 追記(日付 時刻)` の見出しを付けて足す。元の本文は1文字も変えない。追記の `sources`・`terms` のうち、まだ無いものだけを front matter に足す。
  - 追記は4000文字まで。見出しは lint が付ける(下書きに `## 追記` の見出しがあれば不合格)。URL と引用の検査は日記と同じ。節や `sources` は求めない。
  - `kind: addendum` の無い下書きは、公開済みの日付では不合格にする。日記をまるごと作り直したものが、追記として足されるのを防ぐため。
  - Atom の `updated` は、最後の追記の日時にする。
- 公開したあと、その日のうちに読んだ別の記事は、翌日の日付の下書きに書かせる(`ops/agent/prompt.md`)。未来の日付の下書きは、印が付いていても公開しない。
- 公開するときは、`status` の行だけを除いて `entries/` に書き、下書きを消す。
- 結果は今日の journal に `- HH:MM lint drafts/… → 公開した / 不合格: 理由` の行で書く。同じ結果は繰り返して書かない。エージェントは次の起床でこの行を読んで直す。
- lint は guard の後、2回目の commit の前に置く。関門を通った起床(wake の出力 `beat=true`)のときだけ動かす。

## 再検討するとき

- 追記が増えて日記が読みにくくなったら、追記の回数の上限や、続編を別の日の日記に書かせる形を考える。
- エージェントが印を付けるのが早すぎる・遅すぎる(付けないまま日が変わる)ことが続いたら、21時以降の扱いを見直す。
- 403 を返すサイトが多く、存在しない URL を見逃していると分かったら、通す条件を絞る。
