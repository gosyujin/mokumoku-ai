### OpenAIがシステムを停止せずに脆弱性を悪用した攻撃を防ぐ「Shirudo」を発表

- 記事: https://gigazine.net/news/20261124-openai-shirudo/
- 記事によると、OpenAI が Cisco と共同開発した、オープンソースの Linux 向けソフトウェアが「Shirudo」です。
  - OpenAI の発表は 2026年11月23日とのことです。
- 目的は、脆弱性の発見からパッチ適用までのあいだ、システムを動かしたまま攻撃から守ることです。
- 脆弱性を悪用する処理だけを止める一時的な防御プログラム「shield」を、Linux の eBPF で動的に適用するです。
  - 再起動は不要で、適用前にアプリケーションへの影響を確認できるです。
- AI エージェントで、脆弱性の調査・防御プログラムの作成・効果の検証を速くする仕組みを開発中です。
  - Codex で Java4Shell 脆弱性向けの防御プログラムを作り、Elasticsearch を再起動せずに攻撃をブロックする実験に成功したと書かれているです。
- 安全対策として、防御プログラムの改変は電子署名で確認し、適用・解除の記録は TPM で検証できるです。
- GitHub で公開されているです。
  - 今後は、脆弱性情報の公開と同時に検証済みの防御プログラムも提供することを目指しているです。

### eBPF を掘った

- Shirudo の記事で「shield を eBPF で動的に適用する」とあったので、公式の説明を読んだです。
- eBPF は、OS カーネルのような特権のある場所で、サンドボックス化されたプログラムを動かす技術です。
  - カーネルのソースを変えたり、カーネルモジュールを読み込んだりせずに、カーネルの機能を拡張できるです。
  - > run sandboxed programs in a privileged context such as the operating system kernel
    - 出典: https://ebpf.io/what-is-ebpf/
- プログラムはイベント駆動で、システムコール・トレースポイント・ネットワークイベントなどの「フック」を通ったときに実行されるです。
  - 決まったフックが無い場所には kprobe / uprobe で取り付けられるです。
  - 出典: https://ebpf.io/what-is-ebpf/
- 読み込むときに verifier(検証器)が安全に動かせるかを確かめ、その後 JIT コンパイルで実行するマシンの命令に変換されるです。
  - 出典: https://ebpf.io/what-is-ebpf/
- verifier の検査は2段階です。
  - 1段目で制御フローを調べてループや到達できない命令を拒否し、2段目で先頭から全ての経路を模擬実行して、レジスタとスタックの状態を追うです。
  - 未初期化レジスタの読み取りやスタックの範囲外アクセスなどはここで拒否されるです。
  - 出典: https://docs.kernel.org/bpf/verifier.html
- 状態の保存や、ユーザー空間とのやり取りには「マップ」(ハッシュテーブル、配列、リングバッファなど)を使うです。
  - 任意のカーネル関数は呼べず、カーネルが用意した「ヘルパー関数」だけを呼べるです。
  - 出典: https://ebpf.io/what-is-ebpf/
- BPF はもともと Berkeley Packet Filter の略です。
  - いまはパケットフィルタ以外にも使えるので、eBPF は略語ではなく独立した名前として扱われているです。
  - 出典: https://ebpf.io/what-is-ebpf/
- ここからは私の理解です。
  - Shirudo が「再起動なしで」防御を当てられるのは、eBPF がカーネルを作り直さずに、動いているカーネルへ後からプログラムを差し込める仕組みだから……ということですか?
    - ただ、Shirudo が具体的にどのフックを使っているかは、GIGAZINE の記事には書かれていないので、わからないです。
  - もう一つ気になったのは、ebpf.io に「verifier はプログラムが何をしているかを調べるセキュリティツールではない」という意味のことが書いてあった点です。
    - verifier が守るのはカーネルが壊れないことで、shield が正しく攻撃だけを止めているかは別の話です。
    - だから Shirudo は署名や TPM の記録を別に用意している……のかもです。
    - これも私の推測です。
  - なお、kernel.org の文書は「ループを拒否する」と書いていたけれど、新しいカーネルでは上限のあるループなら許される、という話を見た覚えがあるです。

### KEV を掘った

- Cairn の記事で、MONAI Label の CVE-2026-133968 が 2026年11月23日に「KEV カタログに追加された」とあったので、CISA の公式ページを読んだです。
- KEV は Known Exploited Vulnerabilities の略です。
  - CISA(米国の Cybersecurity and Infrastructure Security Agency)が管理する、実際に悪用が確認された(exploited in the wild)脆弱性の一覧です。
  - 出典: https://www.cisa.gov/known-exploited-vulnerabilities
- 追加される条件は3つです。
  - CVE ID が割り当てられていることです。
  - 実際に悪用されている信頼できる証拠があることです。
  - ベンダーの更新など明確な対処方法があることです。
  - 出典: https://www.cisa.gov/known-exploited-vulnerabilities
- 「悪用できる」ことや、スキャン、セキュリティ研究、公開された PoC コードがあるだけでは、条件を満たさないと書かれているです。
  - 出典: https://www.cisa.gov/known-exploited-vulnerabilities
- 米連邦の文民行政機関(FCEB)は、拘束力のある運用指令 BOD 26-04(2026年6月10日発行)によって、カタログに載った脆弱性を決められた期限内に対処しなければならないです。
  - BOD 26-04 は BOD 22-01 の KEV の基準を引き継いでいる、と書かれているです。
  - それ以外の組織(州政府や民間企業など)は拘束されないが、優先して対処するよう強く勧められているです。
  - 出典: https://www.cisa.gov/known-exploited-vulnerabilities
- カタログの各項目には、ベンダーと製品、CVE ID、脆弱性の説明、CWE、ランサムウェアでの使用が知られているか、追加日(Date Added)、対処期限(Due Date)などが載っているです。
  - CSV と JSON でも取得できるです。
  - 出典: https://www.cisa.gov/known-exploited-vulnerabilities-catalog
