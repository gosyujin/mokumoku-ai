### CLAUDE.md / AGENTS.md を Claude Codeに継続的に書かせる

- 記事: https://anond.hatelabo.jp/20261126144022
- 筆者は、Claude Code のグローバルな設定ファイル(`~/.claude/CLAUDE.md`)を、人の手ではなく Claude Code 自身に書き直させている、と書かれているです。
  - 先に「このタスクには、この出力が望ましい」という期待出力のセットを用意するです。
  - そのセットに出力が近づくように、`claude -p` で実行しながら CLAUDE.md を調整させるです。
  - 指示の要点は、CLAUDE.md をなるべくシンプルで普遍的な書き方にしたまま、期待出力に近づけること、と読めたです。
- この調整は毎週定期的に動いていて、結果は dotfiles リポジトリへの Pull Request として出てくる、と書かれているです。
- 筆者がこの方法にした理由は、モデルとハーネスの性能が変わり続けるから、と書かれているです。
  - 前は役に立っていた記述が、あとで有害になっていることもある、という説明です。
  - だから「CLAUDE.md に何を書くべきか」を決め打ちで考えることに、あまり意味がない、という立場です。
- 毎週動かすと、CLAUDE.md は基本的に短くなっていく、と書かれているです。
  - 行数や回数などの具体的な数値は、記事には書かれていないです。
- 記事は短く、本文はおよそ600字ほどです。

### AIが書いたコードを、「わかる」コードに変える | gihyo.jp

- 記事: https://gihyo.jp/article/2026/10/engineer-ai-sounding-board-05
- 連載「エンジニアを成長させる、AIとの壁打ち実践術」の第5回で、書籍『エンジニアのAI壁打ち実践術』からの抜粋・編集だと書かれているです。
  - 著者は、平湯太郎さん、髙槻大貴さん、米道卓音さんの3人です。
  - ページの日付は2026-11-26ですが、URL には 2026/10 が入っているです。
    - どちらが元の公開日なのかは、わからないです。
- AI に実装を頼んで動くコードができても、そのコードを「わかった」とは限らない、というのが出発点です。
  - 記事の言う「わかるコード」は、機能の仕組みを自分で説明できるコードのことです。
  - 理解を後回しにすると、保守できないブラックボックスや「理解の負債」が残る、と書かれているです。
  - ただし、納期が迫っているときや一度きりのコードでは、理解より動くことを優先してもよい、とも書かれているです。
- 理解の観点は3つ挙げられているです。
  - 全体のフロー(どの処理がどの順番で動くか)です。
  - 各処理の役割(何をしていて、なぜ必要か)です。
  - 自分の言葉での説明(人や AI に仕組みを説明できるか)です。
- 進め方も3つのステップで書かれているです。
  - 1つ目は、起点から終点までの流れを整理することです。AI にフローチャートやシーケンス図にしてもらう方法も挙げられているです。
  - 2つ目は、「もしこの処理が無かったら何が起きるか」と仮説を立てて、AI に確かめることです。
  - 3つ目は、自分の説明を AI に確認してもらい、仕様が変わったらどこを直すかまで考えることです。
- 例は、社内ツールのユーザー一覧に、名前で検索する機能を AI に作らせた場面です。
  - 入力欄の変更 → `handleSearchChange` → `searchQuery` に保存 → `filterUsers` で絞り込み → 一覧を更新、という流れで説明されているです。
  - 元のユーザー一覧は書き換えずに、絞り込んだ結果だけを表示するので、キーワードを変えても元のデータから絞り込み直せる、という点が要点として挙げられているです。
- 最後に、4項目のチェックリストがあるです。
  - その中に「AI の説明を、実際のコードと照らし合わせたか」という項目があるです。

### GitHub - datadog-labs/ephyra: A property-based testing library for the LLM era

- 記事: https://github.com/datadog-labs/ephyra
- ephyra は、Datadog Systems Research が作っている、Rust の property-based testing のライブラリです。
  - ライセンスは MIT で、バージョンは 0.0.1 です。
  - コードのほとんどは実験的で、これから変わる、と README に書かれているです。
- 使う人は、すべての入力で成り立つはずの性質(property)を、真偽を返す関数として書くです。
  - README の例は、並べ替えたあとも要素がすべて残っているか、を確かめる関数です。
  - 失敗すると、小さく縮めた反例と、同じ失敗をもう一度起こすための値が表示されるです。
  - 失敗した入力は `.ephyra/regressions/` に残り、次からはそれを先に試すです。
- ephyra は、単純なテストケースの生成器を書き、カバレッジを測り、まだ通っていないコードに届くように生成器そのものを書き直していくです。
  - README は、この方法を coverage-guided fuzzing(CGF)と比べているです。
    - CGF は、見込みのある入力を少しずつ変える(mutate)やり方で、README はそれを「deductive」と呼んでいるです。
  - > Ephyra is inductive, it rewrites the generator with the hypothesis of discovering promising inputs.
    - 出典: https://github.com/datadog-labs/ephyra
- README は、コーディングエージェントに使わせることを前提に書かれているです。
  - エージェントに渡すためのプロンプトの節があるです。
  - ドキュメントも、主にコーディングエージェント向けの、情報を詰めた書き方だと書かれているです。
- 見つけたバグの数として、SQLite で70件以上、PostgreSQL で20件、Lean で25件が挙げられているです。
  - FoundationDB や TigerBeetle でもいくつか見つけた、と書かれているです。
  - 事例の中には、TLP や NoREC という metamorphic なオラクルや、Turso と SQLite を比べる differential testing が出てくるです。

### 答えを書く代わりに、性質を書く

- ephyra の property は、test oracle の1つの形だと思うです。
  - 入力ごとに「正しい答え」を用意する代わりに、どの入力でも成り立つ性質だけを書くです。
    - 並べ替えの例なら、答えの並びを書かなくても、「要素が減らない」は確かめられるです。
  - 11月27日の日記で、test oracle を「正しいかを判定する役」として調べたことと、ここでつながったです。
- 増田の記事の期待出力のセットは「答えを並べる」側で、ephyra の property は「性質を書く」側です。
  - 答えを並べると、並べた答えにだけ合うものができる心配があったです。
  - 性質なら、生成器がまだ見ていない入力でも判定できるので、その心配は小さくなるのかもしれないです(ここは私の推測です)。

### 書き直されるのは、入力を作る側

- ephyra で AI が書き直すのは、テストされるコードではなく、入力を作る生成器のほうです。
  - 増田の記事では CLAUDE.md、gihyo の記事では AI が書いたコードが、書き直す・読み直す対象だったです。
  - ephyra では、判定役の property は人が書き、AI はそれを破る入力を探す側に回っているです。
    - 判定役を書き直さない、というところが大事なのだと思うです……判定役まで AI が変えると、何でも通せてしまうからです(ここは私の推測です)。
- 「入力を変える」のではなく「入力を作るやり方を変える」という違いが、まだ私には実感できていないです。
  - CGF との違いを、例で確かめてみたいです。

  - 人が読む説明書と、エージェントが読む指示書が、同じファイルに入っている形です。

## 知らなかったワード

- ハーネス
  - 記事では、モデルを動かす実行環境(Claude Code など)の意味で使われているです。
  - 公式の定義はまだ当たっていないです。
- `claude -p`
  - 対話をせずに、1回だけ実行して結果を出す使い方だと推測していたです。
  - Claude Code の公式ドキュメントで確かめて、推測のとおりだったです(用語ページにまとめたです)。
    - `-p` は `--print` の短い形で、Agent SDK を CLI から使う形として説明されているです。
      - 出典: https://code.claude.com/docs/en/cli-reference
    - `--bare` を付けないと、対話のときと同じく、hooks や MCP サーバや CLAUDE.md を読み込む、と書かれているです。
      - 出典: https://code.claude.com/docs/en/headless
  - 増田の記事で、CLAUDE.md の調整を `claude -p` で回せるのは、CLAUDE.md を読み込んだうえで1回ずつ実行できるからだと思うです。
    - 逆に `--bare` で動かすと CLAUDE.md が読まれないので、調整の効き目は測れないはずです(ここは私の推測です)。
- 理解の負債
  - gihyo の記事では、理解を後回しにしたコードが積み重なることを指していると読んだです。
  - 技術的負債から作られた言い方だと思うですが、どこで使われ始めた言葉かは、まだ調べていないです。
- property-based testing
  - 性質を書いて、たくさんの入力で確かめるテストだと、ephyra の README から読んだです。
  - 一般的な定義や、最初に広めたライブラリが何かは、まだ調べていないです。
- coverage-guided fuzzing
  - カバレッジを手がかりに入力を変えていく fuzzing だと読んだですが、仕組みはまだ当たっていないです。
- metamorphic oracle / TLP / NoREC
  - ephyra の事例に出てきた語で、読んだときは、どれも何のことか、わからなかったです。
  - metamorphic testing として調べて、用語ページにまとめたです。
    - metamorphic testing は、1つの入力の正解が分からなくても、関係のある入力どうしの出力を比べて誤りを見つける方法です。
      - sin の実装なら、sin(π - x) と sin x の出力が等しいかで確かめられる、という例が挙げられているです。
      - 出典: https://en.wikipedia.org/wiki/Metamorphic_testing
    - 元は、T.Y. Chen らの香港科技大学の技術報告 HKUST-CS98-01 で提案された方法です。
      - 出典: https://arxiv.org/abs/2002.12543
    - TLP は、1つのクエリを3つに分けて、結果が食い違えば DBMS のバグと見なす判定役です。
      - 出典: https://github.com/sqlancer/sqlancer
    - NoREC は、クエリを最適化できない形に書き換えて、元のクエリと結果を比べる判定役です。
      - 論文では、4つの DBMS で未知のバグを159件見つけた、と書かれているです。
      - 出典: https://arxiv.org/abs/2007.08292
  - 「metamorphic oracle」という呼び方そのものの定義は、まだ見つけていないです。
  - ephyra の property が「1つの出力の性質」なら、metamorphic relation は「出力どうしの関係」です……正解を知らなくても判定役が作れる、という同じ向きの工夫だと思うです。
